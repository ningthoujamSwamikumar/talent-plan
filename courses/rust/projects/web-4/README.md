# Project: gRPC and GraphQL (Phase 2, Project 4)

## Introduction

Modern services rarely expose a single API surface. Different consumers have
different needs:

- **REST** (JSON over HTTP) is the lingua franca for web and mobile clients.
- **gRPC** (Protocol Buffers over HTTP/2) is the standard for efficient
  service-to-service communication — strong typing, streaming, and compact
  binary encoding make it ideal for backend microservices.
- **GraphQL** gives frontend teams the ability to request exactly the data they
  need in a single round-trip, avoiding over-fetching and under-fetching.

In this project you will build **all three** interfaces for a task-management
backend. Critically, they all share the **same repository layer** — the
persistence and business logic are written once and reused across every API
surface. This is the architecture pattern used by production systems at scale.

## Part 1 — Protocol Buffers

**Goal:** Define the service contract in `proto/taskforge.proto` and understand
what `tonic-build` generates.

### Key concepts

| Concept | Description |
|---------|-------------|
| `.proto` file | Language-neutral schema for messages and services |
| `tonic-build` | Rust build-script crate that compiles `.proto` → Rust code |
| Wire format | Variable-length integers, length-delimited fields — compact and fast |
| Code generation | Traits for the server, structs for request/response messages |

### Exercises

1. Read `proto/taskforge.proto`. Identify every message and RPC method.
2. Run `cargo build` and inspect the generated code in
   `target/debug/build/taskforge-multi-*/out/taskforge.rs`.
3. Explain why protobuf is more efficient than JSON for service-to-service
   calls.

## Part 2 — gRPC Server

**Goal:** Implement `TaskServiceImpl` — the struct that satisfies the
`TaskService` trait generated by tonic.

### Key concepts

- **`#[tonic::async_trait]`** — the generated trait requires async methods.
- **`tonic::Request<T>` / `tonic::Response<T>`** — wrappers that carry
  metadata (headers, extensions) alongside the protobuf message.
- **`tonic::Status`** — the gRPC error type. Map domain errors (not found,
  validation failure) to the appropriate gRPC status code.
- **Repository injection** — pass an `Arc<dyn TaskRepository>` into
  `TaskServiceImpl` so the gRPC layer stays thin.

### Exercises

1. Implement `create_task`, `get_task`, `list_tasks`, `update_task`, and
   `delete_task`.
2. Map repository errors to `tonic::Status::not_found`,
   `tonic::Status::invalid_argument`, etc.
3. Write a test that creates a task via gRPC and retrieves it.

## Part 3 — gRPC Streaming

**Goal:** Implement `WatchTasks` — a server-streaming RPC that pushes task
events to connected clients.

### Key concepts

- **Server streaming** — the server sends a sequence of messages; the client
  reads them as a `tonic::Streaming<TaskEvent>`.
- **`tokio::sync::broadcast`** — a multi-producer, multi-consumer channel.
  Every mutation (create / update / delete) sends an event; every watcher
  receives it.
- **Back-pressure** — if the client is slow, the broadcast channel drops old
  messages (lagged receiver). Handle `RecvError::Lagged` gracefully.

### Exercises

1. Add a `broadcast::Sender<TaskEvent>` to `TaskServiceImpl`.
2. In every mutation method, send a `TaskEvent` after the repository call
   succeeds.
3. In `watch_tasks`, subscribe to the broadcast channel and yield events
   through a `tokio_stream::wrappers::BroadcastStream`.
4. Write a test that starts a watcher, creates a task, and verifies the watcher
   receives the event.

## Part 4 — gRPC Client

**Goal:** Write a helper client that calls the gRPC service, useful for testing
and as a reference for service-to-service communication.

### Key concepts

- **`TaskServiceClient`** — generated by tonic, connects to the server over
  HTTP/2.
- **Channel** — the underlying HTTP/2 connection managed by tonic/hyper.
- **Interceptors** — middleware that can inject auth tokens or tracing headers
  into every request.

### Exercises

   `TaskServiceClient` calls.
2. Use the client in integration tests instead of constructing raw requests.

## Part 5 — GraphQL Schema

**Goal:** Define `QueryRoot`, `MutationRoot`, and `SubscriptionRoot` using
`async-graphql`.

### Key concepts

- **`#[Object]`** — marks a struct as a GraphQL object with resolver methods.
- **`Context`** — async-graphql's request context, used to access shared state
  (repository, dataloaders).
- **`InputObject`** — strongly typed input for mutations.
- **Schema composition** — `Schema::build(query, mutation, subscription)` wires
  everything together.

### Exercises

1. Implement `QueryRoot` with `task(id)` and `tasks(project_id, page,
   per_page, status)` resolvers.
2. Implement `MutationRoot` with `create_task(...)` and `update_task(...)`
   mutations.
3. Expose the schema at `/graphql` via `async-graphql-axum`.

## Part 6 — DataLoader

**Goal:** Prevent N+1 queries when resolving nested relationships (e.g.,
"list tasks with their project info").

### Key concepts

- **N+1 problem** — without batching, fetching 50 tasks with project info
  fires 1 list query + 50 project queries.
- **DataLoader pattern** — collect keys during a single GraphQL execution tick,
  then fire one batched query.
- **`async_graphql::dataloader::Loader`** — the trait you implement. Return a
  `HashMap<K, V>` from a batch of keys.

### Exercises

1. Implement `ProjectLoader` in `src/graphql/dataloader.rs`.
2. In the `Task` GraphQL type, resolve `project` by calling the dataloader
   instead of the repository directly.
3. Write a test that queries multiple tasks with nested projects and verify
   (via query count or logging) that only one batch query was executed.

## Part 7 — GraphQL Subscriptions

**Goal:** Implement real-time task update subscriptions via WebSocket.

### Key concepts

- **`#[Subscription]`** — marks a struct whose methods return `Stream`s.
- **WebSocket transport** — `async-graphql-axum` upgrades HTTP to WebSocket for
  subscription connections.
- **`graphql-ws` protocol** — the standard subscription protocol used by
  Apollo, Relay, and other clients.
- **Shared broadcast** — reuse the same `broadcast::Sender` from the gRPC
  streaming layer.

### Exercises

1. Implement `SubscriptionRoot` with a `task_events(project_id)` method that
   returns a stream of task events.
2. Wire the subscription into the axum router with
   `async_graphql_axum::GraphQLSubscription`.
3. Write a test that subscribes, creates a task, and verifies the subscription
   delivers the event.

## Part 8 — Unified Server

**Goal:** Run REST, gRPC, and GraphQL from a single binary, sharing the
repository and authentication layers.

### Key concepts

- **Shared state** — `Arc<AppState>` holds the repository, broadcast sender,
  and any other shared resources. Pass it to all three API surfaces.
- **Port separation vs. route separation** — you can run gRPC on port 50051
  and REST+GraphQL on port 3000, or use tonic's `axum` integration to serve
  everything on one port. This project uses port separation for clarity.
- **Graceful shutdown** — `tokio::signal::ctrl_c()` triggers shutdown of both
  servers.

### Exercises

1. In `src/bin/server.rs`, spawn two `tokio::spawn` tasks: one for the
   axum server (REST + GraphQL) and one for the tonic server (gRPC).
2. Share `AppState` across both.
3. Add graceful shutdown so Ctrl+C stops both servers cleanly.
4. Test that you can hit REST, gRPC, and GraphQL endpoints against the
   running binary.

## Running the project

```bash
# Start Postgres (e.g., via Docker)
docker run -d --name taskforge-db -p 5432:5432 \
  -e POSTGRES_DB=taskforge -e POSTGRES_PASSWORD=password postgres:16

# Set the database URL
export DATABASE_URL="postgres://postgres:password@localhost:5432/taskforge"

# Build (compiles proto files) and run
cargo build
cargo run --bin server

# REST:    http://localhost:3000
# GraphQL: http://localhost:3000/graphql
# gRPC:    localhost:50051
```
